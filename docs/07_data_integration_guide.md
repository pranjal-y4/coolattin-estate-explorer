| # | Dataset | File / Source | Format | Records |
|---|---|---|---|---|

## 2. What Each Dataset Contains

### Dataset 1 — `unified_processed.csv` — The People Records
This is the **central dataset** of the entire application. It is a pre-assembled flat file that merges three separate historical estate ledgers into one table:

- **Emigration ledger** — people who emigrated from the Coolattin estate (mainly 1847–1856), with ship name, departure date, arrival date, household list
- **Eviction / clearances ledger** — court records of people evicted or served notices to quit
- **Tenancy / rental ledger** — tenancy survey records listing tenants, their holdings in acres, and rent owed

Each row is one person-record. A person can appear in multiple ledgers — in that case, the row has multiple flags set:

```
has_emigration_record = True/False
has_eviction_record   = True/False
has_tenancy_record    = True/False
```

Key derived columns that were computed during pre-processing:
- `canonical_name` — normalised full name (`forename + surname`)
- `townland_norm` — townland name uppercased for consistent joining (`AGHOWLE LOWER`)
- `family_key` — groups household members (e.g. `murphy|aghowle lower`)
- `is_widow` — derived from title/role text
- `is_canada_destination` — derived from arrival text containing "Quebec", "Montreal" etc.
- `children_count` — sum of `sons + daughters`
- `family_size_estimate` — derived from household composition fields

**This file is not generated by any code in this repo.** It was assembled from archival sources and committed as a permanent seed file.

---

### Dataset 2 — `townlands.json` — Boundaries + Estate Population Surveys
A GeoJSON file with 152 polygon features, one per Coolattin estate townland. Each feature's `properties` object contains:

- `TL_ENGLISH` — the English townland name
- `TL_GAEILGE` — the Irish/Gaelic name
- `AREA` — area in square metres
- `TD_ID`, `GUID` — estate internal identifiers
- **Estate population survey totals** for years: 1827, 1839, 1848, 1850, 1860, 1868 (e.g. `T_POP_1827`, `T_POP_1839_`)
- **Clearances counts** per year 1847–1856 (e.g. `Clearances_1847`, `Clearances_1848`)

These population figures are **estate-survey totals only** (no male/female breakdown). The standard census breakdowns (1841–1891 with male/female/inhabited/uninhabited) come from the VRTI KG or the seed CSVs, not this file.

---

### Dataset 3 — `workhouse_data_final.xlsx` — Workhouse Pauper Register
Two Excel sheets covering different register number ranges:
- Sheet `1-127`: columns `Pauper Name`, `Number in Register`
- Sheet `from 128`: more detailed — `Names and Surnames of Paupers`, `Electoral division`, `Sex`, `Age`, `If Adult...`, `Employment or Calling`, `Religious denomination`, `Name of wife or husband`, `Number of children`, `Date when admitted or born`, `Date when died or left`

The workhouse register has **no townland field** — only `Electoral division`, which maps roughly to a parish-level area. This is why exact townland linking is not possible; only name matching + electoral division proximity is used.

---

### Dataset 4 — VRTI Knowledge Graph (live SPARQL)
The Virtual Record Treasury of Ireland (VRTI) triplestore at `https://virtuoso.virtualtreasury.ie/sparql/`. Queried during the ingest job (not at runtime) for:
- Census records 1841–1891: male, female, inhabited houses, uninhabited houses, per townland
- Townland boundary geometry (WKT polygon)
- Centroid coordinates (lat/lon)
- Civil parish, barony, county hierarchy
- External identifiers (OSM ID, OSI ID, VRTI ID)
- Images and external links (logainm.ie, townlands.ie)

All KG data is **pulled once and stored locally in SQLite**. The live KG is not queried at application request time (except for the optional VRTI enrichment panel in the Ask page, which is a parallel non-blocking call).

---

### Datasets 5 — NMS Heritage Features
Three GeoJSON files from the National Monuments Service open data:
- `holywells_wicklow.geojson` — holy wells in County Wicklow
- `monuments_wicklow.geojson` — national monuments
- `asi_wicklow.geojson` — Architectural Survey of Ireland

Used exclusively by the Heritage page. Not integrated with the people records or the SQLite database.

---

### Datasets 6 & 7 — Census Seed CSVs
- `unified_census.csv` (165 rows): Coolattin estate townlands × 6 census years, with male/female/inhabited counts plus Gaelic names and placename descriptions. Used as a fallback when the VRTI KG is offline during ingest.
- `wicklow-census-data.csv` (1,539 rows): All Wicklow townlands × census years. A broader backup reference, not directly loaded by the application at runtime.

## 3. How the Datasets Are Integrated — The Ingest Pipeline

Integration happens **once, offline**, via two ingest jobs. After they run, the application serves everything from local SQLite and in-memory caches. No external calls are needed at request time (except the optional VRTI enrichment in the Ask page).

### 3.1 `full_ingest.py` — Townland, Census, and Clearances

```
GeoJSON (townlands.json)
        │
        ├── Extract townland names, Gaelic names, area, TD_ID, GUID
        │   → normalize name via townland_service.normalize_townland_name()
        │   → upsert into townland table (SQLite)
        │
        ├── Extract estate population figures (1827–1868)
        │   → insert into census_record table (source='json')
        │
        └── Extract clearances counts (1847–1856)
            → insert into clearances_record table (source='json')

VRTI KG (SPARQL, if online)
        │
        ├── fetch_kg_details() per townland
        │   → overlay: centroid_lat, centroid_lon, wkt_geometry,
        │     civil_parish, barony, county, osm_id, osi_id, vrti_id,
        │     images, links, Gaelic name
        │   → update townland row (source='kg')
        │
        └── get_census_records_for_county('Wicklow')
            → filter to estate townlands only (via estate_name_map)
            → insert into census_record table (source='kg')
            → fallback: unified_census.csv seed if KG returns nothing
```

**Result in SQLite:**
- `townland` table: 152 rows, fully enriched
- `census_record` table: estate survey years (source='json') + standard census years (source='kg')
- `clearances_record` table: 10 years × ~152 townlands

---

### 3.2 Ask Page Ingest — `unified_record` in SQLite

The `unified_processed.csv` is also loaded into a SQLite table called `unified_record`, created and populated by code inside `ask_service.py`. This is a direct copy of the CSV into a queryable relational table.

```
unified_processed.csv (13,707 rows)
        │
        └── _ensure_unified_record_schema()  — create table if needed
            _bulk_insert()                   — insert all rows
            CREATE INDEX ON unified_record(townland_norm)
```

The key column is `townland_norm` (uppercase townland name), which links to `UPPER(townland.name)` in the `townland` table.

---

### 3.3 Workhouse Integration — In-Memory Name Match (No Persisted Join)

The workhouse records are **never written to SQLite**. The link between workhouse paupers and estate people records is computed in RAM once per process startup:

```
workhouse_data_final.xlsx (2 sheets)
        │
        └── get_workhouse()
            → parse both sheets into a DataFrame
            → build wh_by_name dict: { "forename surname": [workhouse_rows] }
               also keys: "surname forename", raw_name

unified_processed.csv (DataFrame in RAM)
        │
        └── get_match_index()
            → for each person in unified CSV:
                compute name variants (forename+surname, surname+forename, canonical_name)
                look up each variant in wh_by_name (exact string match on lowercased name)
                if match found:
                    check electoral_division vs townland/parish (location_match flag)
                    score: location-confirmed matches ranked above name-only matches
            → result: _WORKHOUSE_MATCH_INDEX = { record_id: [matching_workhouse_rows] }
```

This index is a Python dict in memory, keyed by `record_id`. It is **not written back to the CSV or to SQLite**. The unified CSV and `unified_record` SQLite table have no workhouse columns.

## 4. The Final Data Model — What Tables Exist

After both ingest jobs have run, the SQLite database (`coolattin.db`) contains:

### `townland` — 152 rows
One row per Coolattin estate townland. This is the geographic authority table.

| Column group | Source | Content |
|---|---|---|
| `name`, `name_gaelic` | GeoJSON | Canonical English name (UPPER), Gaelic name |
| `td_id`, `guid`, `area_sqm` | GeoJSON | Estate identifiers and area |
| `county` | GeoJSON / KG | "Wicklow" |
| `centroid_lat`, `centroid_lon` | KG | Map pin coordinates |
| `wkt_geometry` | KG | Full boundary polygon |
| `civil_parish`, `barony` | KG | Place hierarchy |
| `kg_uri`, `osm_id`, `osi_id`, `vrti_id` | KG | External identifiers |
| `images_json`, `links_json` | KG | External media and links |

---

### `census_record` — ~1,500 rows
One row per townland × year. Covers estate survey years (totals only, no sex breakdown) and standard census years (with male/female/inhabited/uninhabited).

| Column | Notes |
|---|---|
| `townland_id` | Foreign key → `townland.id` |
| `year` | 1827, 1839, 1841, 1848, 1850, 1851, 1861, 1868, 1871, 1881, 1891 |
| `total` | Population total |
| `male`, `female` | Only for standard census years (1841–1891) |
| `inhabited`, `uninhabited` | House counts, standard census years only |
| `source` | `'json'` (estate survey) or `'kg'` (VRTI standard census) |

---

### `clearances_record` — ~1,500 rows
One row per townland × year (1847–1856). Records the number of evictions/clearances in that townland in that year.

| Column | Notes |
|---|---|
| `townland_id` | Foreign key → `townland.id` |
| `year` | 1847 through 1856 |
| `count` | Number of clearances |

---

### `unified_record` — 13,707 rows
One row per person-record. The primary people table. All 83 Ask page SQL templates query this table.

Key columns for querying:

| Column | Type | Role |
|---|---|---|
| `record_id` | TEXT | Unique identifier (e.g. `CL2868`) |
| `townland_norm` | TEXT | Uppercase canonical townland — the join key |
| `townland` | TEXT | Display townland name |
| `townland_as_shown` | TEXT | Original spelling in the source document |
| `surname`, `forename` | TEXT | Person name |
| `canonical_name` | TEXT | Full display name |
| `year` | INTEGER | Year of the record |
| `role` | TEXT | `'chief tenant'`, `'under tenant'`, etc. |
| `has_emigration_record` | INTEGER | 1 if emigration source |
| `has_eviction_record` | INTEGER | 1 if eviction source |
| `has_tenancy_record` | INTEGER | 1 if tenancy/survey source |
| `is_widow` | INTEGER | Derived flag |
| `is_canada_destination` | INTEGER | Derived from arrival text |
| `ship_name`, `departure`, `arrival` | TEXT | Emigration fields |
| `holding_acres` | REAL | Land holding size |
| `family_key` | TEXT | Groups household members |
| `children_count`, `family_size_estimate` | INTEGER | Derived family fields |
| `chief_tenant_surname/forename` | TEXT | Chief tenant of record |
| `under_tenant_surname/forename` | TEXT | Under tenant if applicable |

**Join to `townland` table:**
```sql
unified_record.townland_norm = UPPER(townland.name)
```

This is how the Ask page gets coordinates, parish, and barony alongside people data.

## 5. What the Home Page Actually Queries

### Page load sequence

**Step 1 — Load all people records into browser memory:**
```
GET /api/unified/records
→ unified_service.search_records() reads unified_processed.csv (DataFrame, cached)
→ workhouse_service.get_match_index() annotates each record with has_workhouse_record
→ returns all 13,707 rows as JSON (no filters applied on initial load)
```

The entire dataset is delivered to the browser as one JSON payload. The browser stores it in `state.records`.

**Step 2 — Load townland name list:**
```
GET /api/unified/townlands
→ returns sorted list of unique townland values from unified_processed.csv
→ filtered against GeoJSON: only townlands that have a polygon are shown in dropdown
```

**Step 3 — Load map polygons:**
```
GET /static/data/townlands.json (served as a static file)
→ Leaflet renders the 152 polygon boundaries directly from this GeoJSON
→ Each polygon's hover tooltip shows the TL_ENGLISH property
```

**Step 4 — Build in-browser indexes:**
`buildIndexes(state.records)` iterates all 13,707 records and builds:
- `state.townlandIndex[townland_name]` — groups records by townland, then by chief tenant, under tenant, and surname
- `state.familyGroups[surname|townland]` — groups records by surname+townland for family linking

**No further API calls happen as the user browses townlands.** All filtering and counting is done in JavaScript against the already-loaded `state.records` array.

### What "people count" means on the home page

When a user clicks a townland polygon or selects one from the dropdown, the panel shows:
- **Tenants** view: grouped by chief tenant → under tenant hierarchy
- **Families** view: grouped by surname, showing all records for that family in that townland

The count displayed (e.g. "42 records in Aghowle Lower") is `state.records.filter(r => r.townland === selectedTownland).length` — a pure in-browser count of rows in `unified_processed.csv` where the `townland` field matches.

It is **not** a SQL query. It is not the number of people who "lived" in that townland — it is the number of estate records (emigration + eviction + tenancy) associated with that townland name. A person who appears in both an eviction record and a tenancy record counts as two rows.

### Census data in the side panel

When a townland is selected, the panel also fetches:
```
GET /api/census/?year=1841&townland=<name>&limit=1
→ census_service.py: DB-first / KG-second
→ queries census_record JOIN townland WHERE year=1841
→ returns population total for that townland in 1841
```

This is the only SQL query triggered by a home page interaction.

## 6. What the Ask Page Queries

The Ask page runs a seven-stage pipeline. Each stage is streamed to the browser via Server-Sent Events (SSE) as it completes.

### Stage 1 — Townland Resolution
Before any SQL runs, the user's question is checked for a townland name.

```
_resolve_townland_context(question, hint)

Priority order:
1. Explicit hint (townland typed in the hint box)
2. Exact name found inside the question text
3. Fuzzy match from question text (via _suggest_townland_matches)

Matching is done against:
→ _townland_catalog()
   SELECT name, civil_parish, barony, county, centroid_lat, centroid_lon,
          COUNT(DISTINCT unified_record.record_id) AS local_record_count
   FROM townland
   LEFT JOIN unified_record ON unified_record.townland_norm = UPPER(townland.name)
   GROUP BY townland.name
   (cached in _TOWNLAND_CATALOG_CACHE, 10-minute TTL)

Scoring (difflib.SequenceMatcher on compact_key):
  exact match     → score = 1.0, match_type = 'exact'
  hint match      → accept if score ≥ 0.82, match_type = 'fuzzy'
  question match  → accept if score ≥ 0.86, match_type = 'fuzzy'

Rank boost:  +0.06 if townland has ≥1 record in unified_record
             +0.02 if county = Wicklow
```

The resolved townland name (`townland_norm`) is injected into all subsequent SQL.

---

### Stage 2 — Four Fast Lanes (first match short-circuits routing)

```
Before intent classification, four lanes are checked in priority order:

Fast Lane 1 — Rule-based slot-fill (semantic_layer.try_rule_based_fill)
  → Match question keywords against 22 metric keyword sets
  → Confidence scoring: starts 1.0, penalised for competing metrics / no filters
  → If confidence ≥ 0.80 → compile SQL directly (0 LLM calls, < 5 ms)

Fast Lane 2 — Verified template
  → _try_verified_analysis(question, townland_norm, analysis)
  → Score 83 QUESTION_TEMPLATES by required_keywords + optional_keywords
  → If match in VERIFIED_ANALYSIS_TEMPLATE_IDS → SQL, confidence = 1.0

Fast Lane 3 — Direct memory reuse
  → Query ask_query_memory (TTL 60 s cache)
  → token_sort_ratio + cosine ≥ 0.55 → reuse approved SQL

Fast Lane 4 — Embedding template retrieval (embedding_index.py)
  → TF-IDF unigram+bigram cosine merged by RRF over templates + memory
  → cosine ≥ 0.68 AND all required_keywords present → use template SQL
```

Example compiled SQL (emigration count, rule-fill path):
```sql
SELECT COUNT(DISTINCT record_id) AS emigration_count
FROM unified_record
WHERE has_emigration_record = 1
  AND townland_norm = 'AGHOWLE LOWER'
  AND year = 1852
```

Example compiled SQL (population trend, semantic layer):
```sql
WITH emigrants AS (
  SELECT townland_norm, COUNT(DISTINCT record_id) AS emigrated_people
  FROM unified_record WHERE has_emigration_record = 1 GROUP BY townland_norm
),
pop_1841 AS (
  SELECT t.name AS townland, c.total AS pop_1841
  FROM census_record c JOIN townland t ON c.townland_id = t.id WHERE c.year = 1841
),
pop_1861 AS (
  SELECT t.name AS townland, c.total AS pop_1861
  FROM census_record c JOIN townland t ON c.townland_id = t.id WHERE c.year = 1861
)
SELECT e.townland, e.emigrated_people,
       p41.pop_1841, p61.pop_1861,
       (p61.pop_1861 - p41.pop_1841) AS population_change
FROM emigrants e
LEFT JOIN pop_1841 p41 ON UPPER(p41.townland) = e.townland_norm
LEFT JOIN pop_1861 p61 ON UPPER(p61.townland) = e.townland_norm
ORDER BY e.emigrated_people DESC LIMIT 30
```

### Stage 3 — Intent Classification → Route Dispatch

```
classify_intent(question, analysis, slot_fill)   ← intent_router.py

COMPARATIVE  → ANALYTICAL (SQL) + RELATIONAL (SPARQL) in parallel
RELATIONAL   → subgraph_engine (VRTI + GraphDB traversal)
ANALYTICAL   → semantic_layer slot-fill → deterministic SQL compiler
FALLBACK     → _generate_sql() via LLM (OpenRouter → Ollama fallback)

ANALYTICAL lane (semantic_layer.py):
  → rule-fill (confidence ≥ 0.80, 0 LLM) OR LLM slot-fill (confidence ≥ 0.70)
  → compile_sql(slot_fill): assembles SQL from 22-metric registry
  → compile_sparql(slot_fill): generates SPARQL equivalent for GraphDB (RQ6)

RELATIONAL lane (subgraph_engine.py):
  → VRTI SPARQL: townland→parish→barony hierarchy, siblings, external links
  → GraphDB: get_entity_neighborhood(name, k=2, max_nodes=40)
  → Qualitative context only; counts always come from SQL

FALLBACK lane:
  → _generate_sql(question, schema, townland_norm, analysis, approved_examples)
  → LLM prompt: annotated schema + question plan + approved examples
  → _sanitize_and_validate_sql(): FORBIDDEN_SQL regex blocks all writes
  → _execute_with_recovery(): run SQL; if error → 1 LLM repair attempt
```

## 8. Key Facts to Remember

1. **`unified_processed.csv` is the single source of truth for all people records.** It exists in two forms at runtime: as a Pandas DataFrame (for home page browsing) and as a SQLite table `unified_record` (for Ask page SQL).

2. **The workhouse match is name-only, in RAM, never persisted.** There is no workhouse column in `unified_record` or in `unified_processed.csv`. The link is computed at startup and lives only in `_WORKHOUSE_MATCH_INDEX`.

3. **`census_record` and `clearances_record` are aggregate/geographic.** They contain totals per townland per year — not individual names. They are populated from `townlands.json` (estate surveys + clearances counts) and the VRTI KG (standard census).

4. **The home page performs no SQL queries after initial load.** All filtering, counting, and grouping of people records happens in the browser against the fully-loaded JSON payload.

5. **The Ask page only ever queries SQLite.** The 83 templates and the LLM fallback all produce SQL that runs against `coolattin.db`. The live VRTI KG is only called in Stage 6 for enrichment context, not for answering the question.

6. **Townland normalisation is the glue.** Every join across tables relies on the same normalisation rule: `UPPER(name)` with whitespace collapsed and brackets/punctuation stripped. `townland_service.normalize_townland_name()` is the single authority for this.
