# SPARQL Competency Questions — Coolattin RDF/KG Prototype (D8)

This document defines five competency questions (CQs) for the Coolattin RDF knowledge graph. Each entry provides:
- The natural-language question
- The equivalent SQLite query (against the local database)
- The SPARQL query (against the local GraphDB repository)
- A comparison note on expressiveness and trade-offs

## RDF Graph Structure

The Coolattin KG is generated by `scripts/rdf_uplift.py` and uses the following vocabulary:

| Prefix | Namespace |
|--------|-----------|
| `co:` | `https://coolattin.ie/ontology#` |
| `ex:` | `https://coolattin.ie/resource/` |
| `schema:` | `https://schema.org/` |
| `xsd:` | `http://www.w3.org/2001/XMLSchema#` |

Key classes and properties:

| Term | Description |
|------|-------------|
| `co:Person` | An individual in the estate records |
| `co:Event` | An event linked to a person (emigration, eviction, tenancy) |
| `schema:familyName` | Surname |
| `schema:givenName` | Forename |
| `co:townland` | Townland name string |
| `co:parish` | Parish name string |
| `co:estate` | Estate name |
| `co:year` | Year of the event (xsd:integer) |
| `co:eventType` | Event category: "emigration" \| "eviction" \| "tenancy" |
| `co:role` | Role in the household |
| `co:occupation` | Occupation string |
| `co:hasEvent` | Links a Person to their Event |
| `co:forPerson` | Links an Event back to its Person |

## CQ1: How many emigration events were recorded per townland?

### SQLite

```sql
SELECT townland, COUNT(DISTINCT record_id) AS emigrant_count
FROM unified_record
WHERE has_emigration_record = 1
GROUP BY townland
ORDER BY emigrant_count DESC;
```

### SPARQL

```sparql
PREFIX co:     <https://coolattin.ie/ontology#>
PREFIX schema: <https://schema.org/>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>

SELECT ?townland (COUNT(DISTINCT ?person) AS ?emigrantCount)
WHERE {
  ?person a co:Person ;
          co:townland ?townland ;
          co:hasEvent ?event .
  ?event co:eventType "emigration" .
}
GROUP BY ?townland
ORDER BY DESC(?emigrantCount)
```

### Comparison

Both queries aggregate by townland and count distinct individuals. The SPARQL version traverses the object graph (`?person co:hasEvent ?event`) while SQL uses a boolean flag column (`has_emigration_record = 1`). The RDF approach is more semantically precise: the event type is an explicit entity rather than a denormalised flag, making it easier to extend with additional event properties (date, ship name) without schema migration. SQL is faster on the local SQLite instance because it has no query planning overhead for graph traversal.

## CQ2: Which surnames appear in three or more distinct townlands?

### SQLite

```sql
SELECT surname, COUNT(DISTINCT townland) AS townland_count
FROM unified_record
WHERE surname IS NOT NULL AND townland IS NOT NULL
GROUP BY surname
HAVING COUNT(DISTINCT townland) >= 3
ORDER BY townland_count DESC;
```

### SPARQL

```sparql
PREFIX co:     <https://coolattin.ie/ontology#>
PREFIX schema: <https://schema.org/>

SELECT ?surname (COUNT(DISTINCT ?townland) AS ?townlandCount)
WHERE {
  ?person a co:Person ;
          schema:familyName ?surname ;
          co:townland ?townland .
}
GROUP BY ?surname
HAVING (COUNT(DISTINCT ?townland) >= 3)
ORDER BY DESC(?townlandCount)
```

### Comparison

The HAVING clause is supported in both SPARQL 1.1 and SQLite. Structurally the queries are near-identical. The SPARQL version benefits from the RDF open-world assumption: if a new data source links a surname to additional townlands via `owl:sameAs` or `skos:exactMatch`, the SPARQL query automatically picks it up without re-ingestion. SQLite requires an ETL pipeline update.

## CQ3: Which townlands experienced both evictions and emigrations in the same year?

### SQLite

```sql
SELECT e.townland, e.year
FROM unified_record e
JOIN unified_record ev ON e.townland = ev.townland AND e.year = ev.year
WHERE e.has_emigration_record = 1
  AND ev.has_eviction_record = 1
GROUP BY e.townland, e.year
ORDER BY e.year, e.townland;
```

### SPARQL

```sparql
PREFIX co:     <https://coolattin.ie/ontology#>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>

SELECT DISTINCT ?townland ?year
WHERE {
  ?emigPerson a co:Person ;
              co:townland ?townland ;
              co:hasEvent ?emigEvent .
  ?emigEvent co:eventType "emigration" ;
             co:year ?year .

  ?evictPerson a co:Person ;
               co:townland ?townland ;
               co:hasEvent ?evictEvent .
  ?evictEvent co:eventType "eviction" ;
              co:year ?year .

  FILTER(?emigPerson != ?evictPerson)
}
ORDER BY ?year ?townland
```

### Comparison

The SQL version uses a self-join on `unified_record`, which works but duplicates person rows. The SPARQL version naturally joins two independent graph paths sharing `?townland` and `?year` bindings — no artificial join key is needed. This is a good example of where graph querying is more expressive: the two event paths are treated as independent sub-patterns that the SPARQL engine intersects by shared variable binding.

## CQ4: What is the population trajectory of a given townland across census years?

### SQLite

```sql
SELECT cr.year, cr.male + cr.female AS total_population
FROM census_record cr
JOIN townland t ON cr.townland_id = t.id
WHERE UPPER(t.name) = 'AGHOWLE LOWER'
ORDER BY cr.year;
```

### SPARQL

```sparql
PREFIX co:     <https://coolattin.ie/ontology#>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>

SELECT ?year (COUNT(DISTINCT ?person) AS ?personCount)
WHERE {
  ?person a co:Person ;
          co:townland "Aghowle Lower" ;
          co:hasEvent ?event .
  ?event co:year ?year .
}
GROUP BY ?year
ORDER BY ?year
```

### Comparison

This query highlights a fundamental data coverage difference: the SQLite census data (from the VRTI KG ingest) includes male/female population totals from official census records (1841–1891), giving accurate headcounts. The RDF graph, built from the estate administration records, contains only individuals recorded in the Fitzwilliam papers — a subset that is useful for tracking family presence but is not a population census. For this CQ, SQL is more accurate; the SPARQL result represents *recorded individuals* rather than total population. This distinction is an important finding for the dissertation's evaluation chapter.

## CQ5: Which persons appear in both the estate records and have a workhouse confidence match of "High"?

### SQLite

```sql
-- The workhouse match index is computed in-process; there is no dedicated
-- SQL table for it. This query approximates by showing persons in townships
-- that had documented workhouse electoral divisions.
SELECT DISTINCT ur.canonical_name, ur.townland, ur.year
FROM unified_record ur
WHERE ur.townland IN (
  SELECT DISTINCT townland FROM unified_record WHERE year BETWEEN 1847 AND 1856
)
ORDER BY ur.townland, ur.year
LIMIT 200;
```

### SPARQL

```sparql
PREFIX co:     <https://coolattin.ie/ontology#>
PREFIX schema: <https://schema.org/>
PREFIX xsd:    <http://www.w3.org/2001/XMLSchema#>

SELECT ?name ?townland ?year
WHERE {
  ?person a co:Person ;
          schema:familyName ?name ;
          co:townland ?townland ;
          co:hasEvent ?event .
  ?event co:year ?year .
  FILTER(?year >= 1847 && ?year <= 1856)
}
ORDER BY ?townland ?year
LIMIT 200
```

### Comparison

This CQ exposes an architectural gap: workhouse matching (computed by `workhouse_service.py`) is an in-process operation that produces ephemeral confidence scores, not persisted triples. To fully answer CQ5 from SPARQL, the uplift script would need to emit workhouse match triples (e.g., `?person co:workhouseConfidence "High"`) during ingest. This points to a concrete dissertation contribution: demonstrating that materialising derived link scores as RDF allows federated querying that the current in-memory approach cannot support.

## Summary: SQL vs. SPARQL Trade-off Table

| Criterion | SQLite | SPARQL (GraphDB) |
|-----------|--------|-----------------|
| Query syntax | Familiar; wide tooling support | Verbose pattern matching; steep learning curve |
| Schema flexibility | Rigid; ALTER TABLE required for new fields | Open-world; new properties added without migration |
| Join complexity | Self-join on shared key required | Shared variable binding across graph paths |
| Aggregation | HAVING, GROUP BY identical to SPARQL 1.1 | SPARQL 1.1 HAVING / GROUP BY equivalent |
| Federated query | Not native | SPARQL SERVICE enables cross-endpoint queries (e.g., VRTI) |
| Derived/computed data | Stored as columns or flags | Must be materialised as triples or computed at query time |
| Performance (local) | Faster on small datasets; index-optimised | Graph traversal overhead on first cold query |
| Open-world assumption | Closed world — absent data assumed false | Open world — absent data is simply unknown |
| Provenance | Not built in; requires audit columns | Native via named graphs, PROV-O |
| Reuse with VRTI KG | Separate HTTP calls; manual stitching | Native SPARQL federation via SERVICE clause |
